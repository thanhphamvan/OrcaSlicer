API Overview
============

Two ways to run Python
----------------------

**Plugins** are loaded by a running OrcaSlicer. They register capability classes
and OrcaSlicer calls back into them — for a slicing hook, a settings page, or a
printer agent. See :mod:`orca`, :mod:`orca.slicing` and :mod:`orca.script`.

**Scripts** are the other direction: you run OrcaSlicer and hand it one file to
execute, and it exits when your script returns. No window opens, no OpenGL is
initialized, no printers are discovered, and installed plugins are not run. See
:doc:`info_cli`.

Both use the same ``orca`` module, and both are the same interpreter — the one
bundled with the application.

``orca`` is not installable
---------------------------

There is no ``pip install orca``. The module is compiled into the OrcaSlicer
binary and only exists inside that process, which is why the reference pages in
this documentation are generated by a script that runs *inside* OrcaSlicer. An
``import orca`` from an ordinary interpreter will fail, and that is expected.

Namespaces
----------

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Namespace
     - Purpose
   * - :mod:`orca`
     - Plugin registration: the ``@orca.plugin`` decorator and capability bases
   * - :mod:`orca.host`
     - The host application: model graph, meshes, presets, geometry, version and
       capability discovery
   * - :mod:`orca.host.project`
     - Owned, read-only project snapshots — the subject of most scripts
   * - :mod:`orca.host.errors`
     - Exceptions shared across the host API
   * - :mod:`orca.host.ui`
     - Native dialogs and plugin windows. Requires a running GUI
   * - :mod:`orca.slicing`
     - The slicing pipeline graph, available inside a slicing hook

Discovering what is available
-----------------------------

The host API has its own version, independent of the application version, and
tells you which services are usable *in this process*:

.. code-block:: python

   import orca

   orca.host.api_version        # (1, 0)
   orca.host.capabilities()     # frozenset({'project.read', 'script.execute'})

An additive change increments the minor version; an incompatible one requires a
new major version and a documented migration.

Only services that are both implemented *and* reachable right now are listed.
A script run from the command line has no GUI, so nothing GUI-dependent appears.
Availability can also change while a GUI is running, so a capability check is not
a guarantee for a later call — every call still validates its own context.

.. code-block:: python

   if "project.read" not in orca.host.capabilities():
       raise SystemExit("this build cannot read projects")

An unavailable service raises
:exc:`~orca.host.errors.CapabilityUnavailableError`, or its subclass
:exc:`~orca.host.errors.ApplicationUnavailableError` when the missing piece is a
running application. It never returns an empty result that looks like success.

The project snapshot
--------------------

:func:`orca.host.project.read` returns a snapshot that **owns** its data. It is
loaded by the application's own importers, and it keeps the native model, the
project configuration, the plate data and the presets embedded in the file.

That ownership is what makes the object graph safe to hold on to:

.. code-block:: python

   project = orca.host.project.read("assembly.3mf")
   instance = project.instances[0]
   mesh = instance.object.volumes[0].mesh()

   del project                                   # the snapshot stays alive
   other = orca.host.project.read("другой.3mf")  # so does everything from it

   instance.object.name      # still valid
   mesh.triangle_count()     # still valid

Reads use the file's own data. They never consult the presets selected in the
GUI, never modify the source file, never change the active project, and never
slice anything.

The object graph
----------------

.. code-block:: text

   Project
   ├── plates      -> Plate    ── instances ──┐
   ├── objects     -> Object   ── volumes ->  │ Volume
   ├── instances   -> Instance <──────────────┘
   ├── unassigned_instances -> Instance
   ├── materials   -> Material
   └── issues      -> Issue

The distinction that matters most: an **object** is a unique definition, and an
**instance** is one placed copy of it. Two copies of one object can sit on
different plates, so group instances by plate, never objects. A multipart object
can also use several materials.

Every instance is on exactly one plate or in ``unassigned_instances`` — never
both, and never neither.

Conventions
-----------

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Convention
     - Rule
   * - Units
     - Millimetres throughout, including files whose declared units needed
       conversion on import
   * - Sequences
     - Tuples, in native import order
   * - Mappings
     - Read-only; assigning to one raises :exc:`TypeError`
   * - Plate index
     - Zero-based sequence position
   * - Material slot ID
     - One-based, and not necessarily contiguous
   * - Entity IDs
     - Opaque, unique **within one snapshot only**
   * - Unknown values
     - ``None``, never a substituted default
   * - Matrices
     - 4x4 affine, row tuples, acting on column vectors ``(x, y, z, 1)``

What this API is not
--------------------

* Not a mutation API. Everything in :mod:`orca.host.project` is read-only.
* Not a slicer driver. Reading a project never slices it, and no estimate here is
  a sliced or printed result.
* Not a sandbox. A script has the privileges of the process running it.
* Not a stable-ID store. Entity IDs are unique inside one snapshot and are not
  comparable across two reads.
